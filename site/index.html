The source

8 fixture passages

0:00 Purpose

The purpose of this cache is to reduce repeated database reads, not to repair an inefficient underlying query.

1:00 Prerequisites

Prerequisites: measure baseline latency and errors, and confirm that this endpoint permits data up to thirty seconds old. Never use this recipe for authorization decisions.

2:00 Rollout

Rollout procedure: shadow reads first, compare the cached and uncached responses, then enable caching for five percent of traffic behind a reversible flag.

3:00 Example, not a rule

TTL example: use thirty seconds for an inventory preview that tolerates stale data. This is an example, not a universal TTL recommendation.

4:00 Rollback

Rollback condition: if the error rate increases by more than one percentage point over baseline, disable the flag and restore uncached reads. Keep monitoring after rollback.

5:00 Tenant isolation

Key example: tenant ID must be part of the cache key. A shared key can expose one tenant's data to another. Test two tenants requesting the same resource ID.

6:00 Trade-offs

The tradeoff is that shorter TTL reduces staleness but increases database load. Benchmark with your own workload; there is no promised speedup.

7:00 What is not specified

This lesson does not prescribe a cache vendor, SDK, or language-specific implementation.

“Is this technique relevant to my slow endpoint?”

First, check what is actually slow.

This cache can reduce repeated database reads. It will not fix an inefficient underlying query. 0:00

The condition matters as much as the idea.

Your endpoint must tolerate stale data. Measure latency and errors first, and don’t apply this recipe to authorization decisions. 1:00

There is no promised speedup.

A shorter TTL reduces staleness but increases database load. Benchmark your workload before deciding the trade-off is worthwhile. 6:00

A useful next step Check whether repeated reads, rather than query cost, are your bottleneck. That is a suggested investigation, not a diagnosis of your app.

“Teach me how to roll this out safely.”

  1. Establish the baseline. Measure latency and errors. Confirm stale data is acceptable; exclude authorization checks. 1:00
  2. Compare before committing. Shadow reads, compare cached and uncached responses, then enable five percent of traffic behind a reversible flag. 2:00
  3. Know when to stop. In this lesson, an error-rate increase greater than one percentage point triggers rollback. Restore uncached reads and keep monitoring. 4:00

What the lesson leaves open It specifies no vendor or SDK. The measurement interval also needs to be defined before an actual rollout. Don’t mistake an illustrative procedure for a complete implementation. 7:00

“Help me apply this to a multi-tenant inventory endpoint.”

For stale-tolerant inventory previews, not permission checks. 1:00

  1. Check freshness first. Thirty seconds is the lesson’s inventory example, not a universal TTL. Confirm what your endpoint permits. 3:00
  2. Keep tenants apart. Include the tenant ID in the cache key. Test two tenants requesting the same resource ID. 5:00
  3. Make it reversible. In this lesson, an error-rate rise greater than one percentage point triggers a return to uncached reads. 4:00

Adaptation to your project Inspect the key builder and add an isolation test if it’s missing. This is a proposed investigation; no repository has been inspected.

Start here

Install ytmd using https://gvkhosla.github.io/ytmd/llms.txt. Read the instructions and installer first. Check dependencies, ask before making system changes, and install the CLI and skill for my agent. Verify with ytmd doctor.

Then restart your agent and give it a video URL and a task.

Prefer your terminal?

macOS

Requires Homebrew.

brew install python yt-dlp
export PATH="$HOME/.local/bin:$PATH"
curl -fsSL https://raw.githubusercontent.com/gvkhosla/ytmd/v0.5.0/install.sh -o /tmp/install-ytmd.sh
sh /tmp/install-ytmd.sh --agent all
ytmd doctor

Linux

First install Python 3.9+ with SQLite FTS5 and pipx.

pipx install yt-dlp
export PATH="$HOME/.local/bin:$PATH"

ytmd doctor

The pinned installer checks dependencies and release checksums. It does not change your shell profile. Install options and PATH setup.

Does it work with every YouTube video?

Videos need available captions, which can contain mistakes or omissions. ytmd doesn’t transcribe audio. An agent should tell you what it actually read, not imply a few search hits cover the whole video.

Who generates the answer?

Your existing agent. ytmd retrieves captions, chapter reads, and timestamped evidence; it doesn’t run a model. The example above is authored synthetic material, not a measured model output or an interactive AI service.

What stays on my machine?

ytmd saves captions to local SQLite and Markdown. Saved content works offline; fetching captions contacts YouTube. What your agent sends to its model provider depends on your agent setup. Browser cookies are only read with explicit consent.

Can I use the CLI directly?

Yes. These examples use Fireship’s JavaScript in 100 Seconds. Commands retrieve evidence, not an AI answer.

Save the source

ytmd add "https://youtu.be/DHjqpvDnNGE" --json

See the outline

ytmd info DHjqpvDnNGE

Gather task evidence

ytmd context DHjqpvDnNGE --query "javascript" --max-chars 4000 --json

Read deeper

ytmd read DHjqpvDnNGE --max-chars 4000 --json
